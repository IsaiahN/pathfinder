**Subject:** Check one separator before you decide whether the framework is worth reading

> Hi [name],
>
> I have one specific output I would like you to check against what you already know. I am not asking you to read the framework first, and I am not asking you to agree with it. If the output does not survive, there is nothing else to look at.
>
> **The output (`general` on the shape, `specified` per domain, not `grounded`):** the question "what distinguishes a general-purpose computer from a system that imitates a computation only under a chosen interpretation" is a union of two conditions, not one property.
>
> 1. **A generator kernel with a closed set and unbounded arrangements.** A general-purpose machine has a fixed, finite instruction set and an unbounded space of programs over it. The program is data the machine can read, so the same hardware generates many functions. An interpretation-only imitation has a fixed arrangement; its variety is in the observer's description, not in the machine's reach. The figure rule is that a set is closed while its arrangements are not (Fig 13 :115), and that a vocabulary without bonds can name a state and cannot name a route to one (Fig 12 :111). A lookup table names states; a program names a route.
> 2. **A ground that does not move when the interpretation changes.** An anchor is "whatever settles the question and does not change its answer because of what any frame thinks" (Fig 2 :29). If the answer to "is this computing?" flips when the observer changes the mapping, the mapping is doing the settling and it is a frame, not a ground. A general-purpose computer's outputs are checkable across many programs; an imposed mapping fits every system equally well and predicts nothing.
>
> What follows: a general-purpose computer is a generator (a reapplicable method crossing scales) and an interpretation-only imitation is a recording of one occasion. A rock under a chosen mapping and a CPU running the same automaton have the same trace but not the same lineage. Convergent derivation and adopted import look identical in the contents and only the record separates them (Fig 8 :51). Capability belongs to machine and habitat, not to machine alone, so a harness proves wiring and never capability (Fig 11 :39, :70).
>
> **What I am not claiming:** that I can hand you a test that labels an arbitrary physical system general-purpose or not. The framework returns a shape, not a name, and "unreachable is a verdict here, not a silence" (Fig 13 :134). The missing thing is a source-discriminating instrument for the implementation relation, not another checklist. I am also not claiming this is settled by experiment; it is `specified` and a candidate.
>
> **What would refute the shape claim:**
> 1. a fixed-arrangement system with no program-as-data kernel generates the full range of a universal machine's outputs across arbitrary inputs, with no interpreter importing the mapping;
> 2. a system whose causal structure does not mirror the automaton still settles every output against an independent ground under counterfactual inputs;
> 3. an observer-independent instrument gives the same compute or not-compute verdict for one system and function under two different interpretations;
> 4. universality and ground settlement turn out to be one condition measured by one instrument;
> 5. one scalar (bits alone or actions alone) decides the separator in both directions.
>
> I wrote these down before sending this. If any one holds, the separator is wrong and I will retract it. A one-line "this fails because..." is more useful to me than agreement. If you would rather not engage, no reply is needed.
>
> **If it survives, and only then:** the sources are below. The figures are the authority, not my summary of them.
> - Verbatim figure text with line numbers (local extract): `FRAMEWORK/reference/03-FIGURES_TEXT.md`
> - The canonical figures README, branch `general-agent`: https://github.com/IsaiahN/tether/blob/general-agent/figures/README.md
> - Turing Machines, Stanford Encyclopedia of Philosophy: https://plato.stanford.edu/entries/turing-machine/
> - Does a Rock Implement Every Finite-State Automaton?, David Chalmers: http://consc.net/papers/rock.html
>
> **If you want to use the machinery:** the formula is in the figures link. Run it on a problem you know well and can check against a ground. Write down what would refute your result *before* you run it, and state the mode of what you get. A reported failure is more useful to me than a reported success.
>
