## The answer in one line

A reproducible computational result is not a number that reappears; it is a **lineage** whose atoms (software versions, data provenance, parameter values, seeds) and bonds (the executable route between them) are recoverable, whose tolerance for agreement is declared before the comparison, and which at least one frame with a different closure ranges against the same unmoving ground. Same code, same data, same seed is repeatability, not corroboration.

## What is deliberately not here

- No personal emails of named individuals.
- No ranking of people by how likely they are to agree.
- No bulk-send plan.

Three reasons, in the figures' own words:

1. **A room does not supply an anchor.** `Fig 7 :35` "A room's agreement is variation, not a verdict. Selection between rooms is where the ground votes." A list of recipients chosen for receptiveness is a room, not a witness.
2. **Correlation disqualifies a verdict.** `Fig 2 :40` "disqualifying for a verdict: agreement about the world is worthless when the agreeing frames share an evidence pool." Re-running the same code on the same data with the same seed draws on one pool.
3. **Asking for trust before a check spends independence.** `Fig 10 :42` "A verifier that can reconstruct the claim cannot verify it." The first contact carries the residual and its refuter, never the framework's interiors.

Legally: unsolicited bulk email to scraped personal addresses breaches GDPR and CAN-SPAM style rules in many jurisdictions and gets the sending domain blacklisted. That is a practical failure on top of the structural one. Public institutional submission routes avoid both.
