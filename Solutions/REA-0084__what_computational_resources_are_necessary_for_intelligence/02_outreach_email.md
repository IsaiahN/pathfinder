# Outreach draft: check the shape before deciding about the theory

**Use:** one to one, or as a cover letter attached to a submission through the public venues in `03_public_contact_points.csv`. **Not** for bulk send.

**Hard precondition:** do not send until the three strains in `01_figure_grounded_audit.md` §8 are recorded in any reply that discusses them. The shape must survive contact with a checker or the two-stage offer collapses.

---

**Subject:** One checkable claim about compute and capability, before any theory

> Hi [name],
>
> I am working on a question from computational limits research: what computational resources are necessary for intelligence, and are there fundamental efficiency limits? I have one specific output I would like you to check against what you already know. I am not asking you to read the framework first, and I am not asking you to agree with it. If the output does not survive, there is nothing else to look at.
>
> **The output (`specified`, not `grounded`):** the question as posed re-censes into a different question. The figure set I am using says directly, *"What is intelligence? The wrong question, and this figure is the replacement for it"*, and answers instead that capability is a property of agent and habitat, never of the agent alone. So a budget asked about a system in isolation is aimed at the wrong denominator.
>
> Three things follow structurally, and each is written so you can refuse it:
>
> 1. Cost has two currencies that do not add. One prices the description, one prices finding out whether it holds. A single efficiency figure that sums them is the named error in the source text, not the fix for it.
> 2. "Fundamental limit" names two different facts. One is a budget ceiling: the needed thing is already reachable and more search finds it. The other is a barrier: no search inside the same set of primitives adds a primitive. Only an import from a different frame crosses the second. These two issue different instructions, and a single efficiency curve cannot represent both.
> 3. No finite budget arrives. Every additional room closes some of the gap and no finite number of them arrives. This is a limit on arrival, not a number on a curve.
>
> A fourth claim is a budget warning, not a verdict: FLOPs, parameter counts, benchmark scores, and compression achieved are quantities the measured frame also produces. They are useful for choosing what to try first. They cannot settle whether capability moved.
>
> **What I am not claiming:** that I can give you a number of FLOPs, a parameter count, or an efficiency constant. The source framework returns a shape, not a name. It cannot say which primitive is missing, because naming one would already be holding it. I am also not claiming that extra compute never helps. For a budget-limited gap, more search is exactly the right remedy.
>
> **What would refute the shape claim:** I wrote these down before sending this.
> 1. A measurement in which a purely agent-internal increase in compute, with contact held fixed, moves the ground.
> 2. A single accounting that prices description cost and settlement cost in the same units without loss.
> 3. A search inside a fixed set of primitives that adds a primitive to that set.
> 4. A case in which underivability and budget limitation issue the same instruction.
> 5. A finite last room after which nothing further can be asked.
>
> If any one holds, I withdraw the shape. A one-line "this fails because..." is more useful to me than agreement. If you would rather not engage, no reply is needed.
>
> **If it survives, and only then:** the sources are below. The figures are the authority, not my summary of them.
> - The verbatim figure text with line numbers (local repository path): `FRAMEWORK/reference/03-FIGURES_TEXT.md`
> - The eight-step formula and mode rule (local repository path): `FRAMEWORK/figures/THE_FORMULA.md`
> - Physical limits review, Markov 2015: https://arxiv.org/html/1408.3821v2
> - Computational capacity of the universe, Lloyd 2002: https://arxiv.org/abs/quant-ph/0110141
>
> **If you want to use the machinery:** it is in the figures link. Run it on a problem you know well and can check against a ground. Write down what would refute your result *before* you run it, and label the mode of what you get. A reported failure is more useful to me than a reported success.
